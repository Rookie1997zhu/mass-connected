# 详细报价与履约流程升级方案

## 目标与范围

### 已确认的产品口径
- 买家可对比多家供应商报价，显示供应商真实企业名称，但不显示联系人、电话、邮箱等直联信息；所有金额只显示平台加价后的客户价。
- 供应商可修改自己的报价，截止到买家确认方案；买家可修改 RFQ，截止到首个供应商报价产生。
- 买家确认方案后自动生成合同和付款单，并在 MY PAGE 查看正在进行的生产订单。
- 履约首版采用固定五阶段：订单 → 采购 → 生产 → 出库 → 物流；买家可清楚看到当前阶段、整体进度和历史状态。
- 每个阶段可上传 BOM、采购单、不良报告、样品图等文件，全部对买家可见；Excel 支持站内只读预览。
- 不建设物料、库存、采购明细等完整 ERP 模块；合同正式模板和不良报告正式模板后续替换，首版先提供可替换的默认模板。

## 可行性与需修正的冲突
- 整体可行：现有 [backend/apps/rfq/models.py](backend/apps/rfq/models.py)、[backend/apps/project/models.py](backend/apps/project/models.py)、[backend/apps/contract/models.py](backend/apps/contract/models.py) 已具备 RFQ、报价、订单、合同、付款、阶段和文件骨架。
- 价格冲突必须修复：当前买家页面显示加价后价格，但确认方案后订单、合同和付款使用供应商底价。新增不可变的供应商价、客户价和加价率快照，合同及付款统一使用客户价，避免后续修改加价率导致历史订单变价。
- 商业模式冲突已按确认口径调整：显示真实供应商名称会增加绕开平台联系的风险，因此仅显示企业展示名，不暴露联系方式和原始底价。
- 报价修订冲突必须修复：当前管理员可标记“需修订”，但后端禁止供应商再次提交。改为更新原报价并保留修订版本/时间，方案确认后锁定。
- 流程命名冲突：商城 `Order` 与 RFQ 的 `ProductionOrder` 是两套订单；本次履约全部关联 `ProductionOrder/Project`，不改商城订单。
- 文件安全冲突必须先处理：当前 `/media/*` 可通过 URL 直接访问，不能真正保护 BOM、采购单等文件。改为鉴权下载/预览接口，再上线在线预览。

## 实现步骤

1. **统一报价展示、修改权限和价格快照**
   - 扩展 [backend/apps/rfq/models.py](backend/apps/rfq/models.py) 与迁移：为确认后的订单保存 `supplier_amount`、`customer_amount`、`markup_percent_snapshot`，新增报价修订时间/版本；新增字段先设可空或默认值，兼容存量数据。
   - 调整 [backend/apps/rfq/serializers.py](backend/apps/rfq/serializers.py)：买家方案返回供应商企业展示名和加价后价格，永不返回底价、联系方式或当前 `markup_percent`；供应商接口只返回自己的底价。
   - 调整 [backend/apps/rfq/views.py](backend/apps/rfq/views.py) 和路由：供应商可 PATCH 自己未锁定的报价；买家可 PATCH 自己尚未产生供应商报价的 RFQ；方案确认后所有相关报价和 RFQ 进入只读状态，并返回稳定错误码。
   - 管理端继续控制哪些报价对买家可见；买家只比较已审核、已开放的供应商方案，避免未经平台审核的报价直接曝光。

2. **修正确认方案后的合同与付款金额**
   - 在方案确认事务中计算并冻结供应商价、客户价和加价率快照；[backend/apps/contract/services.py](backend/apps/contract/services.py) 和付款创建逻辑改用客户价，供应商订单视图使用供应商价。
   - 对存量订单采用兼容回退，不根据当前加价率反推历史金额；无法可靠确认的历史记录保持旧口径并标注为旧数据。

3. **建立可替换的合同模板能力**
   - 在合同域增加版本化 `ContractTemplate`，支持合同号、甲乙方、RFQ、订单、客户价、交期、付款条件等占位符；签发时保存模板版本/渲染内容快照。
   - 复用现有 PDF 生成基础设施，买家确认方案后自动生成默认合同 PDF；后续收到正式模板时只新增并启用模板版本，不修改已签发合同。
   - 保留 MY PAGE 合同查看、下载和签署流程；付款仍在合同生成后创建。

4. **将项目履约统一为五阶段并显示当前节点**
   - 调整 [backend/apps/project/services.py](backend/apps/project/services.py)，新项目默认创建“订单、采购、生产、出库、物流”五个有序阶段；已有项目不强制覆盖。
   - 阶段按顺序推进：仅当前阶段可设为进行中，完成后自动激活下一阶段；项目返回 `current_stage`、完成比例和阶段时间。
   - 更新 [frontend/src/views/mypage/MyPageView.vue](frontend/src/views/mypage/MyPageView.vue)、买家项目/生产订单详情和 [frontend/src/views/supplier/SupplierProjectDetailView.vue](frontend/src/views/supplier/SupplierProjectDetailView.vue)，以清晰的五步进度条展示当前节点；该界面属于功能型 `internal/conservative` 改造，沿用现有视觉体系。

5. **阶段文件、默认不良报告模板与安全访问**
   - 为 `ProjectFile` 增加可空 `stage` 关联，并扩展分类：`bom`、`purchase_order`、`defect_report`、`sample_image`；校验阶段必须属于同一项目。
   - 供应商上传时必须选择阶段和文件分类，文件统一对买家可见；管理员和买家均可按阶段查看。首版提供可替换的默认不良报告 Excel 模板。
   - 收敛 Caddy 公开媒体访问，改为经过项目归属和角色校验的下载/预览接口；继续限制文件大小，并增加 MIME/文件签名校验。

6. **Excel 与图片在线预览**
   - 前端按需引入 SheetJS `xlsx`，以只读弹窗预览 `.xlsx/.xls/.csv`，支持多工作表切换、行列上限和大文件提示；图片使用站内预览弹窗。
   - 解析结果只作为预览，不修改原文件；复杂图表、宏和透视表明确提示可能无法完整还原，保留下载原件入口。
   - 所有新增文案补齐中/韩/英/日 i18n，并统一走现有请求封装层。

7. **验证与回归**
   - 后端覆盖：跨买家/供应商越权、底价与联系方式不泄露、RFQ/报价修改锁定、价格快照一致、合同/付款金额一致、阶段顺序、文件归属和鉴权访问。
   - 前端覆盖：多供应商加价后报价对比、确认方案、MY PAGE 进行中订单、五阶段当前节点、各阶段文件上传与 Excel/图片预览。
   - 执行迁移可回退验证、后端检查/API 冒烟、前端 lint/build，并在 Docker Compose 环境完成端到端回归。

## 风险与缓解
- 供应商真实名称可能促成线下绕单：只显示审核后的企业展示名，不显示任何联系方式；若后续风险不可接受，可无迁移切回匿名别名。
- 存量订单缺少客户价快照：不自动猜测历史价格，仅对新订单执行新口径。
- 大型 Excel 可能阻塞浏览器：懒加载解析、限制渲染行列，必要时使用 Web Worker；复杂 Excel 只保证数据预览，不保证原样排版。
- 全部文件对买家可见可能暴露供应商采购成本：这是已确认口径；上传界面仍需明确提示“客户可见”，防止误传内部文件。
- 正式合同/不良报告模板尚未提供：使用版本化默认模板，正式模板到位后替换新版本，不影响历史文档。

## 验收标准
1. 同一 RFQ 的多个已开放方案展示供应商企业名和加价后客户价，不返回供应商底价及联系方式。
2. 供应商在方案确认前可修改自己的报价；确认后修改返回明确业务错误。买家在首份供应商报价前可修改 RFQ，之后锁定。
3. 买家确认方案后，页面价格、生产订单客户价、合同金额和付款金额完全一致；供应商侧仍显示自己的供应商价。
4. 合同 PDF 自动生成并保存在 MY PAGE，模板版本和签发内容不可被后续模板修改影响。
5. 新项目自动生成五阶段，买家和供应商都能看到当前处于哪个流程，阶段只能按顺序推进。
6. 每个阶段均可上传指定文件；买家可见全部阶段文件，跨订单或无权限用户无法通过 URL 获取文件。
7. Excel 可在网页内切换工作表并只读预览，图片可直接预览；不支持的复杂内容有清晰提示且可下载原件。
8. 中/韩/英/日文案齐全，后端权限/金额/文件测试、前端 lint/build 和 Docker 端到端冒烟均通过。

## 建议的下一步
确认本方案后再进入按方案实现。建议按“报价与金额一致性 → 合同模板 → 五阶段履约 → 文件安全与预览”的顺序分批交付，避免一次上线同时改变价格、合同和文件权限。

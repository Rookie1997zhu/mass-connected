# 缺陷修复（bugfix-harness）

## 何时使用

- 用户报告 **bug**、异常行为、回归、线上/测试环境错误，需要修复而非新功能设计。
- 用户说「修这个报错」「定位原因」「最小改动修复」。

**不适用**：从零做功能用 `feature-planning` / `feature-implementation`；仅需看日志与复现链路的深度运行时排查可组合 `debug-after-test`。

---

## 执行原则

1. **根因优先**：区分现象与根因；说明推断依据（日志、栈、代码路径、复现步骤），避免只对症状打补丁。
2. **最小修复**：在满足根因修复的前提下，改动行数与影响面最小；不借机重构无关模块。
3. **不吞异常**：修复后错误路径仍应有可观测行为（日志、稳定错误码），符合项目 API 与日志规范。
4. **数据边界与权限**：若 bug 涉及数据查询或接口，修复后须再次确认多租户/组织级隔离与权限未被削弱。
5. **证据**：结论须可复核（复现步骤、修复前后对比）；无法验证时标注「无法验证」及原因。

---

## 标准流程

1. **复现**：最小复现步骤；环境（本地/Compose/分支）与数据前提。
2. **定位**：从报错栈、日志、最近变更缩小范围；必要时读取相关规则与 `debug-after-test` 中的专项检查（如 DRF 导入、接口冒烟）。
3. **根因陈述**：一两句说明根本原因（非仅现象）。
4. **最小补丁**：描述或实施最小改动；若有多解，优先风险低、可回滚的方案。
5. **回归检查点**：列出必须再测的项（接口、页面、权限、边界）；注明是否与权限或数据边界相关。

---

## 输出模板（必须）

1. **复现**：步骤与环境。
2. **根因**：简明结论 + 依据。
3. **修复说明**：改了什么、为何足够、未动哪些邻近代码。
4. **回归检查点**：编号列表（必测）；可选标「自动化 / 手动」。
5. **残留风险**：若有（竞态、数据脏、仅缓解未根治），显式写出。

---

## 与其他技能的组合

- **日志与 Compose**：需要看服务日志、容器状态时组合 `debug-after-test`、`docker-deploy`。
- **自检**：修复合并或发布前建议 `self-check-after-change`。
- **审查**：提交前可用 `review-harness`。

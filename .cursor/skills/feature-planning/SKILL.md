# 功能方案设计（feature-planning）

## 何时使用

- 用户要做**新功能、较大改版、多文件/多模块**改动，且尚未有书面方案或验收口径。
- 用户明确说「先设计方案」「出技术方案」「列步骤和风险」「写验收标准」。
- 需求描述模糊，需要先对齐再编码。

**不适用**：已有经用户确认的详细方案且仅差执行时，改用 `feature-implementation`；纯修 bug 用 `bugfix-harness`。

---

## 执行原则

1. **先对齐目标，再谈实现**：用少量问题澄清业务目标、用户角色、约束；避免假设未写明的需求。
2. **方案可执行**：步骤须对应到具体动作（改哪些层、是否动库、是否动接口契约），避免空泛条目。
3. **范围显式**：写清「做 / 不做」，默认 **YAGNI**，不主动扩展用户未要求的能力。
4. **与仓库规则一致**：API、多租户或组织级数据边界、i18n、请求层等须引用并符合 `.cursor/rules` 中的基础约束；后端细节可交叉阅读 `backend-feature-guide`、`backend-migration-and-model`（若涉及模型迁移）。

---

## 标准流程

1. **理解**：一句话概括目标；列出已知输入、输出、非目标。
2. **拆解步骤**：按依赖顺序编号（例如：契约与字段 → 后端 → 前端 → 迁移/配置）；每步注明涉及路径或模块类型（不必臆造不存在的文件路径，可写「待打开仓库后确认」）。
3. **风险**：技术风险、数据风险、兼容性、权限与数据边界、性能；每条给出缓解或验证方式。
4. **验收标准**：可检查、可拒绝的条目（行为、错误码、边界、权限、文案 key 等）；避免「体验良好」类不可验证描述。
5. **确认点**：列出需要用户拍板的一处或多处（若有）；未拍板前不进入实现阶段。

---

## 输出模板（必须）

交付时按以下结构输出（可用 Markdown 标题）：

1. **目标与范围**：做 / 不做。
2. **实现步骤**：编号列表，含依赖顺序。
3. **风险与缓解**：表格或列表。
4. **验收标准**：编号列表，尽量可自动化或人工一步验证。
5. **建议的下一步**：例如「确认后进入 `feature-implementation`」或「需先补充产品口径」。

---

## 与其他技能的组合

- 涉及 **API/模型/迁移**：设计阶段在方案中引用 `backend-feature-guide`、`backend-migration-and-model` 的检查项；实现阶段由对应技能执行。
- 方案确认后的实现与提交前审查：依次使用 `feature-implementation`、`review-harness`，必要时 `self-check-after-change`。

# 按方案实现（feature-implementation）

## 何时使用

- 用户已提供**经确认的**方案、设计摘要、任务列表或上一阶段 `feature-planning` 产出，并要求「按方案做」「逐步实现」「不要加戏」。
- 用户明确限定「只做列表里的几项」「不要动某某模块」。

**不适用**：尚无确认方案时，先用 `feature-planning`；纯缺陷修复用 `bugfix-harness`。

---

## 执行原则

1. **范围冻结**：仅实现方案与验收标准中已列内容；若发现方案遗漏或矛盾，**先说明并请求补充/确认**，不自行扩大范围。
2. **逐步交付**：按方案步骤顺序实现；每完成一步，用一句话说明对应步骤编号与已满足项，避免一次改过多文件难以审查。
3. **遵守项目规范**：命名、API、多租户或组织级数据边界、i18n、异常与日志等遵循 `.cursor/rules`；后端新功能遵循 `backend-feature-guide`；模型/迁移遵循 `backend-migration-and-model`。
4. **不引入无关重构**：不重排无关目录、不顺手「优化」未要求代码；确需触碰相邻代码时写明理由且保持最小 diff。
5. **验证**：每步完成后按方案中的验收项做力所能及验证；全量收尾时使用 `self-check-after-change`（若用户需要环境级验证）。

---

## 标准流程

1. **复述范围**：用列表列出本次将实现的步骤编号与明确不做项（可与用户方案对齐）。
2. **逐步编码**：严格按步骤顺序；一步内仍保持最小变更面。
3. **步骤完成标记**：每步结束后对照方案验收子项勾选或说明证据（命令输出、请求结果等）。
4. **收尾**：汇总改动文件、未实现项（若有，须为方案外且已拒绝或延期）、建议的回归动作。

---

## 输出模板（必须）

1. **范围复述**：本轮回合实现的步骤 / 明确排除项。
2. **已执行步骤与结果**：与方案编号对应。
3. **改动摘要**：主要文件或模块（路径级）。
4. **验收对照**：方案中的验收项 → 本轮回合的满足情况（含「无法在本环境验证」须显式写出）。
5. **建议下一步**：例如运行 `self-check-after-change`、或进入 `review-harness`。

---

## 与其他技能的组合

- **前端界面**：同时遵循 `frontend_art_direction_skill` 中的类型判断与实现顺序。
- **部署与自检**：需要环境验证时组合 `docker-deploy`、`self-check-after-change`。
- **提交前**：由用户或会话触发 `review-harness`。
